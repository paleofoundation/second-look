# Image conventions — Microbiome Signatures

Durable rules so every image on microbiomemedicine.com is indexable by Google Images and
legible to LLM answer engines, with zero per-page hand-tuning. Most of this is enforced
automatically at render; the parts that need a human are the **filename**, the **format
choice**, and confirming the **AI-generated alt/caption**.

> The format itself is rarely the SEO bottleneck. What ranks an image is the semantic
> envelope around it: a descriptive filename, a precise `alt`, a real caption, page
> context, `ImageObject` structured data, and an image-sitemap entry. We generate all of
> those; you mainly have to name and classify the file correctly.

## 1. Format tiering

| Image type | Format | Why |
| --- | --- | --- |
| Logos, icons, certification marks | **SVG** | infinitely scalable, tiny |
| Diagrams, pathways, signature charts, anatomical line art | **SVG** | crisp, scalable, embedded text labels help crawlers |
| Photographs, anatomical/AI renders, microscopy, histology | **WebP** | best quality-to-size for raster |
| New raster content art | **WebP** | — |

Never add a new **PNG or JPG** as content art — convert it to WebP first (see §5). Never
convert an existing SVG to raster. Existing legacy files are grandfathered (we do not
rename or re-host them); these rules bind **new** images.

**Placement — an icon/emblem goes in the hero-left slot, not inline.** A single-subject
mark that represents the whole page — a logo, a certification badge, a condition/microbe
emblem, or a **STOP caution graphic** — belongs in the left sidebar hero area, rendered as:

```html
<div class="research-hero__left">
  <img src="/wp-content/uploads/<yyyy>/<mm>/<name>.svg"
       class="img-autosize research-hero__left-image" alt="…" />
</div>
```

This is the `research-hero__left-image` slot; the render transform treats it as the hero
(eager load, `fetchpriority="high"`, explicit dimensions, **no caption**) and it drives the
`ImageObject` / OG card. Do **not** drop a page-representative icon into the article body as
a `wp-block-image` lead figure — that placement is reserved for **in-body explanatory
diagrams** that illustrate a specific passage (those get a `<figure>` + subtle
`<figcaption>`, see §4). If a page already has a hero-left image, additional in-body diagrams
are fine; there is only ever **one** hero-left icon.

## 2. Filename

Kebab-case, keyword-rich, describing the subject — not `image.png`, `IMG_8726.jpg`, or
`ChatGPT-Image-….png`. Front-load the most specific terms (condition, pathogen, anatomy,
mechanism).

```
mycobacterium-tuberculosis-lung-cavities-microbiome-signature.webp   ✅
pulmonary-tuberculosis-cavitary-lesions.webp                         ✅
tb.png                                                               ❌
lungs-final-v2.png                                                   ❌
```

Store new uploads under `public/wp-content/uploads/<yyyy>/<mm>/` (the `add` command in §5
does this for you). Root-relative paths only — never absolute `https://…` to our own host.

## 3. Alt text

One sentence, **≤125 characters**, medically precise, starting with the subject (no "image
of"/"illustration of"). Generated by AI-vision from the actual pixels + page context and
stored in `image_meta` (see §6). Decorative images (avatars, UI icons) keep an **empty
`alt=""`** — that is correct, not a defect.

```
Pulmonary tuberculosis with cavitary lung lesions and alveolar destruction from M. tuberculosis.
```

## 4. Captions

A subtle visible `<figcaption>` is added **only** to substantive in-body content figures —
never to the hero illustration, never to decorative images. The caption text is also fed
to `alt` (as a fallback) and to the `ImageObject.caption` in structured data **regardless
of whether it is shown**, so crawlers/LLMs always get it. One authoritative sentence, plain
text, no "Figure 1." prefix (the styling handles presentation).

## 5. Adding / converting images (tooling)

`sharp` is a devDependency (build-time only; never shipped to the runtime).

```bash
# Add a NEW image the right way: convert to WebP under public/wp-content/uploads/<yyyy>/<mm>/
npm run img:convert -- add ~/Downloads/source.png mycobacterium-tuberculosis-lung-cavities-microbiome-signature

# Convert existing raster content diagrams in a folder to sibling .webp (never deletes
# originals; skips logos/favicons/screenshots via denylist)
npm run img:convert -- public/wp-content/uploads/2025/12

# (Re)generate the default social card public/og-default.webp
npm run img:og

# Flag non-compliant images (warn-only gate)
npm run img:lint
```

## 6. How indexing works (automatic — don't hand-edit markup)

- **Render transform** — `normalizeImages()` in `src/lib/textRules.ts` (run via
  `applyTextRules`, the same chokepoint as the citation rules) processes every `<img>` at
  render: classifies it (`src/lib/imageClassify.ts`), adds `loading="lazy"` +
  `decoding="async"` (hero gets `fetchpriority="high"` instead), injects width/height +
  the AI `alt`, and wraps captioned content figures in `<figure class="rgbc-figure">` +
  `<figcaption class="rgbc-figcaption">`. It is idempotent and only adds — it never
  reorders captured markup, so `wp_render` stays pixel-exact.
- **Data store** — `image_meta(src, kind, alt, caption, width, height)` keyed by
  normalized root-relative `src`, loaded once per request by `getImageMeta()`
  (`src/lib/imageMeta.ts`). One row per unique image (dedups an image used on many pages).
- **Structured data** — `buildJsonLd()` in `src/lib/seo.ts` emits an `ImageObject`
  (contentUrl, caption, width/height, `representativeOfPage`, Organization creator) for
  the page's hero. `buildMetadata()` sets OG/Twitter images.
- **Image sitemap** — `src/app/sitemap.ts` attaches `images: [hero]` to each page entry
  with a hero, producing the Google `<image:image>` sitemap extension.

## 7. The shared meta contract (single source of truth)

A page's hero is `content_items.meta.hero_image` (root-relative) or
`item.featured_image_url`. Per-image alt/caption/dimensions live in the `image_meta` table
keyed by `normSrc(src)`. When you add a hero:

1. Put the WebP under `public/wp-content/uploads/<yyyy>/<mm>/` with a compliant name (§2).
2. Set `meta.hero_image` to its root-relative path.
3. Add an `image_meta` row: `{ src, kind: 'hero', alt, caption, width, height }`
   (regenerate alt/caption with the vision batch, or write them by hand following §3–§4).

That's all — schema, sitemap, OG, lazy-loading, dimensions, and captions follow
automatically.

## 8. Classification reference

`classify()` in `src/lib/imageClassify.ts`:
- `decorative` — gravatar avatars, `/static_media/`, `/wp-content/themes/`,
  `/wp-includes/`. Never captioned, never in schema/sitemap, `alt` left as-is.
- `content` — `/wp-content/uploads/**` (non-icon). Gets alt + dims + (if a caption
  exists) a figure/figcaption.
- `hero` — a `content` image flagged via `image_meta.kind = 'hero'`; eager-loaded,
  representative ImageObject, never captioned in-body.
